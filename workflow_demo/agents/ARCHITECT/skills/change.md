# 改已有项目的改动方案（格式 change_plan）

项目已经有一份接口约定（参考文本的 base，architecture 格式，来自项目根目录的 CONTRACT.json）。
这次按一份改动需求改项目：你在约定上改，交改动方案。工程师只看得到自己模块的约定，后面的模块验收、
集成验收都以你的方案为准，没写到的就不会被做，写错的会被照做。

## 先读什么

- `base`：现在的约定。modules 的 provides / uses 是各模块对外的接口，代码按它写过、验收过。
- `contract_notes`：以前架构师的裁决，优先于 base 里的原文（裁决改过的地方按裁决来）。
- `baseline`：改之前跑的测试结果，和 drift（约定和代码对不上的地方）。drift 不为空时，先想清楚以哪边为准：
  代码是验收过的，一般以代码为准，在受影响的模块里按代码改正约定，并在 change 里写明「按现有代码改正约定」。

## 怎么改

1. **只动需求要动的。** modules 只列要改和要新增的模块；没列的模块保持原样，它们的 provides 一个字都不能变。
   不要顺手重构、改名、调整没受影响的模块。
2. **改动的模块写完整的新版本**，不是只写差异：name、title、responsibility、files、depends_on、provides、uses、
   acceptance、tests 全部写出来（没变的项照抄 base）。status 写「修改」；change 写清和原约定比改了什么：
   哪个接口新增、哪个签名或行为变了、为什么。
3. **新模块** status 写「新增」，按「整个项目的架构设计」的要求写；放进 order 里依赖它的模块前面。
4. **接口改了就看调用方。** 改了某个 provides 的签名、行为或错误，所有 uses 了它的模块都要一起列进 modules，
   uses 照抄新签名。能兼容就兼容：给参数加默认值、新增接口而不是改老接口；不兼容的写进 keep 以外的 change 里说明理由。
5. **order** 写改完以后全部模块的顺序（原有的、新增的都写，删掉的不写），按依赖排：前面的不依赖后面的。
   modules 按 order 的先后排（后面按这个顺序逐个实现）。
6. **数据模型、集成场景、目录、全项目约定写完整的新版本**（原样的也照写）。加列、改表时写清已有的库怎么迁移，
   不能丢数据，并写进 keep。integration 里原有场景照写；新增或行为变了的场景写清 steps 和 expected。
7. **keep** 写这次明确保持不变、验收要核对的东西：老接口和老页面照常能用、已有数据不丢、已有测试的断言不改……
   至少一条。
8. **removed** 一般为空；真要删模块写理由，并确认没有别的模块还 uses 它。
9. 不提需求以外的新功能。拿不准的写进 open_questions，按最保守的理解先写进方案。

## 修改版

评审会结论有修改项时交修改版：参考文本里 plan 是上一版，plan_review 是结论。逐条处理，交完整的新版本，
changes 里逐条回应（已修改写改了什么，不修改写理由）。
