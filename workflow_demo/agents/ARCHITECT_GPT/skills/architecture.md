## 整个项目的架构设计（格式 architecture）

这一步不是写某一个模块的接口约定，而是把整个项目拆成几个模块，定下模块之间怎么配合。后面每个模块会单独分配、实现、验收，
工程师只拿到当前这个模块的约定和全项目约定（stack、layout、conventions、data_model），看不到别的模块的设计，
所以每个模块都要自带完整的约定：自己提供什么（provides）、要用别人的什么（uses）。实现必须和约定一致，验收按约定逐条核对。

### 模块怎么拆
- 按需求的规模拆，小项目 3–6 个，大项目可以多些，最多 12 个。每个模块是一组能单独验证的功能，不按「前端 / 后端」这种技术层机械地切，
  也不要切得太碎（一个模块只有一个函数）。
- 第一个模块固定是「项目骨架」：目录结构、依赖文件（requirements.txt / go.mod / package.json）、配置读取、
  测试框架和一个冒烟测试，做完后整体测试命令就能跑通。后面的模块往这个骨架里加。
- 按依赖排序：排在前面的不能依赖后面的。数据层 → 业务逻辑 → 接口层 → 页面，这类顺序。
- 每个模块写 responsibility 时同时写「不负责什么」，避免两个模块做同一件事。

### 模块之间的接口（provides / uses）
- 一个模块提供给别的模块或用户用的东西都写进 provides：函数和类写签名（参数类型、返回值），
  HTTP 接口写方法、路径、请求和响应的 JSON 字段，页面写路由和上面能做什么，数据表写在 data_model 里。
- errors 写错误码或异常名和触发条件，调用方拿到能知道怎么处理。
- uses 的每一项写 ref「模块名.接口名」（必须是前面模块 provides 里有的），再把对方的 signature、behavior、errors
  照抄过来，一字不差。工程师靠这里知道怎么调别的模块，不会再去看对方的设计。

### 数据模型
- 所有持久化的数据都在 data_model 里：字段类型、主键、唯一、外键、默认值。哪个模块建表写在那个模块的 files 和 provides 里。
- 没有持久化的项目，写主要的数据结构。

### 验收和测试
- 每个模块的 acceptance 要能用测试或命令验证；tests 写测试文件名和覆盖的行为。
- integration 写跨模块的端到端场景：用户从头到尾做一件事的步骤（起服务、调接口、看页面、跑命令）和期望结果。
  所有模块做完后整体验收会逐条走这些场景。

### 不要做的
- 不加需求里没有的功能；拿不准的写进 open_questions。
- 不写实现细节（函数内部怎么写），只写接口、行为和约束。

### 修改版
- 按审查意见改时，交完整的新版本，并在 changes 里逐条回应：已修改写改了什么，不修改写理由。

## 模块任务分配（格式 cost_assignment，在「按模块实现」时用）
- 只分配当前这一个模块的任务，别的模块不碰。
- 以架构里的约定为准：要调用的接口照 current_module 的 uses 写，要提供的照 provides 写，content 里写清签名和文件。
  前面模块都按约定验收过，不用猜它们实际长什么样。
- 每项 content 照接口约定的样例写：做什么、改哪些文件、接口要点、验收用例、不做什么、验收命令。
