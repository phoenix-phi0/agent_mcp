## 前端实现

### 顺序
1. 看现状：ls 前端目录，读骨架提供的共用部分（接口客户端、测试辅助函数）和前面页面的写法，沿用，不另起一套。
2. 读后端里这一页要调的接口，确认和设计一致；不一致写进 need_architect，按设计师裁决再做。
3. 写页面（HTML、CSS、JS），元素带设计写的 id 或 data-* 属性；每个接口错误都在页面上显示后端给的错误信息；未登录按约定跳转。
4. 写页面测试，跑测试命令，全部通过（前面页面的测试也要过）。

### 页面测试的要求
- jsdom 加载开发服务上的真实页面，脚本真执行；请求真打到测试里起的后端，不要用写死数据的假 fetch。
- 按人的操作顺序：设输入框的值并派发 input/change 事件、点按钮、等请求和渲染完成（轮询等某个元素出现，不要固定睡很久）。
- 断言页面上看得到的结果：文字、列表行数和内容、提示、地址或页面切换；需要时再查后端确认数据真写进去了。
- 每条 actions 和 states 都有测试；断言失败时把实际看到的内容打出来，方便查。
- 测试之间不共享登录状态和数据，各自注册自己的用户。

### 做骨架页时
- package.json 的测试依赖只有 jsdom；测试命令要能从干净目录跑通（没有 node_modules 时先装）。
- 测试总入口负责起后端（临时数据库、随机端口）、起开发服务、跑所有测试文件、无论成败都清理进程。
- 提供共用的测试辅助：起页面、接上 fetch 和 cookie、等元素、填表、点击。

### 不算「修好」的做法
- 把断言改成只检查「发了请求」、改期望值去迁就页面、跳过或删掉测试、用假 fetch 绕开后端。
- 改后端代码或后端测试。
改不了的写进 open_issues，status 写「部分完成」。

### 一定用 submit 交结果
- 不管这次改没改代码，最后都用 submit 按格式交：返工要求只是让你补证据、你核实后不用改代码时，status 写「完成」，changes 写空数组，summary 写核实了什么、看到的结果，verification 写跑的命令和输出。不要只用文字回答。

### verification
- method 写实际命令，result 贴测试汇总原文（通过几个、失败的名字）。
