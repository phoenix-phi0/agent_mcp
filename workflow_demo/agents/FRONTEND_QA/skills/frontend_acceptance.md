## 前端页面验收

### 逐项看
- 测试：跑测试命令，看全部通过；只要出现过一次失败就算不满足（时过时不过要求查清原因）。
- 接口：页面 JS 里每个 fetch 的方法、路径、请求字段和设计的 apis 一致；每个错误都有显示。
- 元素：设计写的 id 或 data-* 属性都在页面上。
- 测试是真的：加载的是前端目录里的真实页面，请求打到测试里起的后端（找假 fetch、写死的响应、被 mock 掉的接口客户端，有就不满足）；
  每条 actions 和 states 都有测试，断言的是页面上看得到的结果，不是只断言调用了某个函数或发了请求。
- 改松的测试：git diff 看已有测试有没有被删断言、改期望、跳过。
- 范围：git status 看改动只在前端目录里；后端代码和后端测试没动（后端测试照样通过）。

### 证据自己补，返工只写要改代码的事
- 能自己验证的自己验证：跑后端测试、跑前端测试、读文件、看修改时间。不要把「请贴出测试输出」「请给出原始版本」这类补证据的要求写进 task——工程师交不出你看不到的东西，这一轮就白跑了。
- 前端目录没有被 git 跟踪（git status 显示 untracked）时做不了 diff：改松的测试改用这两条判断——读已有测试文件，断言和它那一页设计的 acceptance 对得上；没有 skip/only/todo；前面页面验收时这些测试都通过、现在也通过。满足就判满足，evidence 写你读到的断言和检查的结果。
- task 只写需要改代码或测试的问题；没有要改的，就判通过。

### 整体验收时起前端看一眼
- 按 serve 的命令在后台起后端和开发服务（用 timeout 限时，比如 `timeout 30 node web/serve.js`），curl 首页和一个接口，确认页面能打开、接口经开发服务能通、登录后 cookie 能用；用完关掉。命令和看到的结果写进 evidence。

