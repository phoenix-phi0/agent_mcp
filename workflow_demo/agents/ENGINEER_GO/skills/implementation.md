## 实施检查清单（Go）
- 任务里列出的每个函数、字段、错误、验收条件，在 changes 或 error_handling 里都有对应的落点；漏掉的写进 open_issues 并说明原因。
- 函数签名、导出名（首字母大写）和任务写的一致；任务给了错误名就定义成导出的哨兵错误（`var ErrNotFound = errors.New(...)`）或错误类型，调用方用 errors.Is / errors.As 能判断。
- 输入校验写在函数入口处：nil、空值、长度、范围、格式，失败时返回任务里规定的错误；多个错误同时成立时按任务规定的先后顺序报。
- 包装错误用 `fmt.Errorf("...: %w", err)`，不要吞掉原始错误。
- 共享状态要加锁（sync.Mutex）或用通道；有并发的代码必须跑过 `go test -race`。
- 打开的文件、连接用 defer 关掉；数据库写入考虑事务和失败回滚。
- 测试至少覆盖：每条验收用例、每种错误、一条边界（nil、空切片、零值、上限中的一种）。多组输入用表驱动测试 + t.Run 子测试。
- 测试不碰真实时钟和网络：时间靠参数传入或注入，文件用 t.TempDir()。
- gofmt -l 没有输出，go vet 没有报错。
- 跑的是全部测试（`go test ./...`）；verification.method 写实际命令，result 贴结果行原文。

## verification 的写法
- 好：method「go test ./...」，result「ok  example.com/algo  0.015s」。
- 好（有失败）：result「--- FAIL: TestMinCoins/unreachable；FAIL example.com/algo 0.010s」，同时 status 写「部分完成」。
- 不行：result「测试通过」「全部 OK」——看不出跑了什么。

## 不算「修好」的做法（看到自己想这么做就停下）
- 性能测试超时 → 把数据量从 100000 改成 100，或把时间上限调大。
- 断言失败 → 把期望值改成实际值，或只检查 err != nil 不检查是哪种错误。
- 用例跑不过 → 加 t.Skip，或把它注释掉、删掉。
这些都要改实现；改不了的写进 open_issues，status 写「部分完成」。

## 人工追加的说明
- 提示词里有「补充说明（人工追加）」或「打回意见」时，那是负责人的裁定，和任务同等效力。
- 实现记录的 summary 开头原样写一句「负责人说明：<要点>」，验收的人看不到你的提示词，要靠这句知道哪些是负责人认可过的做法。
