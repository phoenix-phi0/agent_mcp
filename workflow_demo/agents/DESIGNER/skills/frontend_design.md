## 前端界面设计（格式 frontend_design）

### 先读后端
- 找到所有 JSON 接口（路由文件、蓝图前缀），逐个读：方法、路径、请求体字段和校验规则、成功响应的字段、每种错误的状态码和响应体。
- 弄清会话怎么做（cookie 名、登录和登出接口、未登录访问受保护接口返回什么）。
- 弄清后端怎么在测试里起：工厂函数、要传的配置（数据库路径、密钥）、怎么建表。test_harness 要写到工程师能照做。

### 页面怎么拆
- 第一页固定是前端骨架（name=skeleton）：目录、package.json（测试依赖只有 jsdom）、开发服务、测试脚本（入口给的测试命令要能跑通）、
  共用部分（接口客户端、登录状态、导航、错误显示、样式）和一个冒烟测试（起后端、加载首页、断言页面出来了）。shared 里写清每个共用部分的导出和行为。
- 后面每页是一个用户能独立完成的一件事（登录注册、列表、编辑、填写、结果……），按依赖排序；小项目 4–8 页。
- 每页写 purpose 时同时写不负责什么，避免两页做同一件事。

### 同源和 cookie
- 页面和接口必须同源，cookie 会话才能用：开发服务把静态文件和接口放在同一个端口下（例如 Node 标准库写的小服务：静态文件直接给，/api 开头的原样转发给后端，Set-Cookie 原样带回）。
- serve 写清启动命令、端口、后端地址从哪读（环境变量，有默认值）。

### 测试怎么跑（test_harness）
- 测试命令跑一个总入口：用临时数据库起一个真后端（随机空闲端口），起开发服务指向它，再逐个跑页面测试，最后清理进程和临时文件；任何一个失败退出码非 0。
- 页面测试用 jsdom 加载开发服务上的真实页面（url 是开发服务的地址，脚本真执行），页面里的 fetch 打到开发服务，cookie 跟着 jsdom 的 cookie jar 走。
  jsdom 没有 fetch：骨架要提供一个把 window.fetch 接到 Node fetch、读写 jsdom cookie jar 的辅助函数，所有测试共用。
- 测试按人的操作顺序：填输入框、派发 input/change 事件、点按钮、等请求完成，断言页面上看得到的东西（文字、列表行、提示、地址变化）。

### 每一页写到什么程度
- apis：照后端代码写；页面要处理的错误都列出来。
- elements：每个要测的元素给 id 或 data-* 属性，测试靠它定位。
- actions：一条一个操作，expect 写看得到的结果（显示什么、跳到哪）。
- states：空数据、接口出错（显示后端给的错误信息）、未登录（跳登录页）各怎么显示。
- acceptance 每条都能用页面测试验证；tests 写测试文件名和覆盖的操作。

### 端到端场景（flows）
- 写跨页面的主要流程：注册登录 → 建东西 → 用它 → 看结果，每步写在哪一页、做什么、看到什么。

### 不要做的
- 不加需求里没有的功能；不要求改后端；拿不准的写进 open_questions。

### 修改版
- 按评审结论改时交完整的新版本，changes 里对每条 todo 逐条回应：已修改写改了什么，不修改写理由。

## 设计确认（格式 contract_decision）
- 工程师报告设计和后端对不上：读后端代码确认真实行为，按真实行为修改约定，detail 写出新的请求和响应。
- 设计没写到：补充约定，写清以后照什么做。工程师理解错了：判按原约定，写清怎么改回去。
