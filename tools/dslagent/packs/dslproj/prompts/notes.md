## 这类任务的规划要点
- 目标：做出约定里的全部表、函数、接口，使 加载检查 无问题、比对约定 一致、跑用例 全过（验收就查这三样，查的是你改完之后的项目）
- 先看用户消息里的约定和现有文件：services/<模块>.zs 往往已有骨架（函数头齐全，函数体是 `报错 501 未实现`），把函数体换成约定「伪代码」描述的实现，函数头一字不改
- 需要新建的文件：entities/<模块>.entity（约定「## 表」里每个表一个实体）、queries/<模块>_*.sql（业务用到的每条 SQL）、routes/<模块>.zs（约定「## 接口」里每个接口）；只能写这些路径（和已有的 services/<模块>.zs），写别的会被拦下
- 上游模块只能按用户消息里列出的公开函数头调用（`调用 上游.函数 键=值`，且本模块 依赖 里要写它）；不要改上游模块的任何文件
- 数据存取一律走 queries/*.sql + db 包动词（查一行 / 查一值 / 查询 / 写库）；数值参数在 SQL 里 CAST；表名、列名必须和实体一致
- 写法：把所有文件内容一次写进脚本末尾的 #改法 段（已有骨架用 `@@ 改` 抄原文，新文件用 `@@ 新建`），再用 改文件 一次套上；不要为了写文件调模型
- 套上后依次 加载检查、比对约定、跑用例；全过就 终止 成功。有问题时把三份报告 + 现有文件交给 派任务 补改一轮（edits），再 改文件 套上、重跑三项检查；仍不过 终止 失败，原因写清哪一项没过（补改会自动读全本模块文件和本模块与全部上游的 entities 原文，不用在报告里重复贴字段）
- 不要写 #清单、#期望表（这类任务不用）；#范围 不用写（范围由系统定）
- 第一行 用包 common text code dslproj，第二行 预算 调用 N 秒 M（N 是 1–12 的正整数；M ≤ 900）；脚本末尾只放 #改法 段
